# 我把一个人脸检测 Demo 做成了能真正跑起来的考勤客户端

最开始写这个项目时，我的目标很简单：打开摄像头，检测到人脸，点一下按钮，把姓名和时间写进文件。代码不长，演示效果也很直观。摄像头前站个人，画面出现绿色框，文本文件多一行记录，看起来已经像个考勤系统了。

但我很快发现，这个版本其实只回答了“画面里有没有脸”，没有回答“这是谁”。姓名仍然靠手工输入，只要镜头前出现任何一张脸，就可以替别人打卡。记录写进文本文件，没有事务，没有查询，也没有办法可靠地处理重复打卡。它更像一个界面演示，离真正使用还差得很远。

## 第一个改动：先把身份这件事做实

我没有一上来就选择体积很大的深度学习模型，而是先用了 OpenCV 自带的 LBPH。原因很实际：这个项目要在普通 Windows 电脑上离线运行，部署简单、启动快和不上传人脸数据，比追求榜单精度更重要。

建档时，我会连续采集 20 张人脸，把每张脸裁剪成 160 × 160 的灰度图，再做直方图均衡化。运行时，Haar 分类器负责找到人脸位置，LBPH 负责返回员工标签和识别距离。距离越低，说明当前人脸与建档样本越接近。默认阈值设为 65，同时要求同一个员工连续识别稳定后才启用打卡按钮。

我特意保留了“确认打卡”这一步，没有让程序看到脸就自动写记录。考勤设备通常放在人员走动频繁的位置，自动触发很容易把路过的人也记进去。多一次确认，反而更符合实际使用习惯。

## 文本文件很省事，但不适合继续凑合

原版把记录追加到 `attendance_records.txt`。只做演示时没有问题，但一旦加入员工状态、上班和下班、导出、删除人脸、历史审计，文本文件就会迅速失控。

我把数据迁到 SQLite，拆成员工、人脸样本、考勤记录、设置和审计日志几张表。写考勤时使用即时事务，先检查员工状态和最近一次打卡时间，再决定是否插入记录。这样即使按钮被连续点击，也不会在几秒内写出一串重复数据。

这里还踩到一个很典型的 Windows 问题。最初我的查询代码用了 SQLite 连接的上下文管理器，以为离开 `with` 后连接就会关闭。测试清理临时数据库时，Windows 一直提示文件被占用。我才确认 SQLite 的上下文管理器只负责提交和回滚，并不会替我关闭连接。后来我给所有查询连接补了明确的生命周期，相关测试才稳定下来。

## 上线要求往往藏在“不正常”的时候

摄像头正常、光线合适、数据库可写时，程序跑通并不难。真正费时间的是那些不正常的情况：摄像头被其他程序占用、画面过暗、员工离镜头太远、数据库目录不可写、依赖装错、管理员忘记先建档。

我在后续版本里取消了“摄像头失败就使用测试图片”的降级逻辑。这个设计放在演示程序里很方便，放到正式考勤里却很危险，因为测试图片也可能产生一条看似真实的记录。现在摄像头不可用时，界面会明确阻止打卡，并允许重新连接。

我还增加了三项基础画面检查：平均亮度过低、平均亮度过高、拉普拉斯方差过低。它们不能代替活体检测，但能拦住一部分因为逆光、过曝和抖动造成的错误识别。员工建档和日常识别使用同一套质量门槛，避免采集阶段把模糊样本永久写进数据库。

## 1.1 解决了两个真实的管理问题

只记录“打卡”还不够，所以 1.1 增加了上班和下班两类事件。数据库升级时，旧记录会保留，并统一标记为“签到”。迁移之前，程序会先用 SQLite 的备份接口生成一份升级前副本，再修改表结构。

另一个问题是重复建档。同一个人如果使用两个工号录入，会直接破坏考勤可信度。我在保存新员工前，让刚采集的样本先经过现有识别器。如果足够多的样本都以较低距离指向同一名员工，就取消保存，并提示管理员检查。员工本人重新采集时会排除自己的标签，所以不会被这条规则挡住。

## 公开仓库前，我又清理了一遍

1.2 没有堆新功能，我主要处理发布质量。

原来的视觉测试使用了一张常见的人脸测试图。它在计算机视觉教程里随处可见，但图片的公开授权并不清晰。我不想因为“大家都在用”就把它继续放进仓库，于是改成用 OpenCV 代码生成确定性的灰度纹理。测试仍然会完整跑一遍 LBPH 训练、预测和重复身份判断，同时不再依赖外部人像文件。

我也补齐了安装脚本、GitHub Actions、许可证、贡献说明和安全说明。PowerShell 安装脚本还有一个小坑：旧版 PowerShell 不会因为外部程序返回非零退出码就自动停止。第一次依赖下载失败时，脚本居然继续打印“安装完成”。后来我显式检查 `$LASTEXITCODE`，才让失败真正表现为失败。

这些工作没有绿色识别框那么显眼，但它们决定了别人克隆仓库以后，能不能看懂、装好、跑通，以及出问题时能不能找到原因。

## 我对这个版本的判断

现在的版本适合课程项目、内部原型和有人值守的低风险考勤。它的优点是依赖少、完全离线、普通电脑就能运行，数据也只留在本机。

它的边界同样明确。LBPH 对光照、角度和外观变化比较敏感；目前没有专业活体检测，手机视频和高质量照片仍然可能骗过系统；单机 SQLite 也不适合多门店或大量终端同步。

如果继续往下做，我会优先处理活体检测和排班规则，而不是继续调整界面颜色。对考勤系统来说，识别结果能否被信任，比看起来像不像一个完整产品重要得多。
